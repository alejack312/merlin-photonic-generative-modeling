# Phase 17.1 Learnings: Trainability Follow-Up: Bandwidth & Init Sensitivity

## Decisions

### Fixed sigma grid replaces the original per-n sigma-schedule recommendation
17.1-RESEARCH.md's own primary recommendation (anchor a single sigma-ratio to one reference n, then derive `sigma(n)` per n) was superseded post-research by the owner: run the CORE sweep 6 independent times, once per fixed sigma value in `{0.03, 0.1, 0.3, 1.0, 3.0, 9.0}`, held constant across the whole n-range, rather than one sigma-schedule sweep.

**Rationale:** the schedule approach requires picking one arbitrary anchor point (n=2's ratio vs. n=5/6's ratio test different hypotheses and are both defensible); the fixed-grid approach avoids that ambiguity entirely and matches the sibling project's own `AC12` bandwidth-sweep precedent and this project's existing convention of sweeping one fixed hyperparameter across the full n-range per run.
**Source:** 17.1-RESEARCH.md ("Owner Decisions" section, resolved 2026-08-12)

---

### TRAIN-10 hyperparameters fixed at scale_factor=1.0, n_draws=1
The paper (Recio-Armengol et al.) leaves the weight-2 covariance scale factor fully free (searched `[0.0001, 1.0]` empirically across unrelated datasets, no principled default transfers). The owner fixed it at `1.0` (the paper's upper bound, making weight-2 angles directly equal to raw covariance) as a single stated spot-check, not a hyperparameter sweep. `n_draws` was set to `1` since the init recipe has no random component -- 100 draws would produce 100 bit-identical theta vectors, a ~100x compute waste.

**Rationale:** TRAIN-10's success criteria ask for one new init scheme's result, not a scale-factor sweep (a sweep would be a MoSCoW scope violation); n_draws=100 for a deterministic scheme is wasted compute with zero statistical benefit.
**Source:** 17.1-RESEARCH.md ("Owner Decisions" section); 17.1-05-PLAN.md Task 1

---

### Mixed-scope weight-2-pair override: covariance-based theta replaces the per-qubit value for the weight-2 pair's own indices
This project's `mixed`-scope circuit has no independent weight-2-only parameter -- `thetas[i]`/`thetas[j]` serve double duty as both qubit i/j's own weight-1 phase and the weight-2 gate's input. Recio-Armengol et al.'s paper assumes an ansatz with separate two-qubit-gate angles, which this circuit lacks. The chosen translation: for `mixed` + `data_dependent`, qubits `i,j` (the weight-2 pair) get the covariance-based `weight2_data_dependent_theta` value in place of their own per-qubit `arcsin(sqrt(mean))` value; every other qubit keeps the standard weight-1 rule.

**Rationale:** this most closely honors the paper's intent (parameters touching the two-qubit interaction get the covariance-based rule) given this circuit's actual single set of n knobs. Stated explicitly per this project's CLAUDE.md "no silent unilateral design decisions" rule, and restated in docs/trainability-study.md so the owner could override it on review.
**Source:** 17.1-03-PLAN.md objective; 17.1-03-SUMMARY.md "Decisions Made"

---

### Per-cell sigma embedded directly in chunk filenames, not just passed as a function argument
Draw-chunk `.npy` files store raw gradients but not which sigma produced them. Retrofitting sigma onto the existing draw-chunking machinery created a real correctness risk: a `combine_chunks` call at a different `--sigma` than the `run_chunk` calls that produced its input files could silently mix gradients computed under different kernels. Fix: `_chunk_path` embeds `sigma{sigma:g}` in the filename itself, and `combine_chunks`' glob pattern requires the same sigma.

**Rationale:** turns a silent semantic mismatch into a loud `FileNotFoundError` (no matching chunk files found) rather than a data-corruption bug that would only surface downstream.
**Source:** 17.1-02-PLAN.md Task 2 (17.1-RESEARCH.md Pitfall 2); 17.1-02-SUMMARY.md

---

### Follow-up analysis lives in a new sibling script, not inside the canonical output-generator
`trainability_analysis_1701.py` was created as a genuinely separate root-level script rather than modifying `trainability_analysis.py` in place, even though the latter is structurally generic enough to be extended.

**Rationale:** `trainability_analysis.py` is Phase 17's canonical, already-shipped output-generator, referenced by `docs/trainability-study.md` as-is; keeping it untouched avoids any risk of altering an already-verified artifact while still reusing its core statistical primitive (`trainability/curve_fit.py::fit_and_compare`) completely unmodified.
**Source:** 17.1-RESEARCH.md (`trainability_analysis.py` section); 17.1-05-PLAN.md objective; 17.1-05-SUMMARY.md "Decisions Made"

---

### `data_dependent` init scheme special-cased inside `pooled_gradients_for_cell`, not inside `sample_thetas`
Unlike `small_angle`/`uniform` (both genuinely random draws dispatched via `sample_thetas(rng, n, init_scheme)`), `data_dependent` needs `p_real` and `weight2_pair` -- context `sample_thetas`'s signature doesn't carry -- and has no per-draw randomness to re-sample. It is computed once per `(n, generator_scope)` cell before the draw loop, with `draw_rng` still called (but unused) to keep the loop structure uniform.

**Rationale:** avoids growing `sample_thetas`'s signature with scheme-specific optional kwargs for a scheme that isn't actually random; keeps the chunking machinery's loop shape uniform across all three schemes.
**Source:** 17.1-03-PLAN.md Task 1; 17.1-03-SUMMARY.md "Decisions Made"

---

### "Weakens" classification threshold: a self-chosen, documented 50% drop in decay rate or AIC margin
The plan asked for a "material" shrinkage distinction between "survives" and "weakens" without specifying a number. The analysis script defines this explicitly as a 50% drop in either the fitted exponential decay rate `b` or the AIC margin (`poly_aic - exp_aic`) relative to the sigma=0.1 baseline, stated in a `MATERIAL_SHRINK_THRESHOLD` constant.

**Rationale:** not an external statistical convention -- a stated, inspectable cutoff chosen because the plan text didn't fix one, avoiding a silently-picked-but-undocumented number.
**Source:** 17.1-05-SUMMARY.md "key-decisions" / "Decisions Made"

## Lessons

### Retry only the failed cell, not the whole invocation, on transient MemoryError
During the multi-hour TRAIN-09 sigma-grid sweep, weight1's n=6 cells hit Perceval's transient `MemoryError: bad allocation` roughly half the time (8 of 16 n=6 invocations across the 6 sigma values), and mixed hit it once. Free system memory was confirmed as low as ~800MB-1.3GB during a failing attempt, recovering to 6-7GB once the failing process exited -- consistent with STATE.md's already-documented ~1GB-free-memory constraint, not a new failure mode.

**Context:** the CLI's per-row flush+fsync (and per-chunk `.npy` files for chunked cells) made every retry a clean single-cell resume with no data loss. No cell needed more than one retry across the entire 6-sigma-value grid for either scope. No OS-level process-management action was taken against processes this session didn't itself start, per a standing safety rule from a prior incident.
**Source:** 17.1-04-SUMMARY.md "Issues Encountered" item 1

---

### Verify determinism by rerunning the affected cell in isolation before concluding a discrepancy is a logic bug
Task 3's bit-for-bit consistency check (new sigma=0.1 sweep vs. Phase 17's original CSVs) found 6 of 18 mixed-scope rows (all `small_angle`, at n=2,3,4) differing by ~1e-13 to 1e-16 relative magnitude, not exact matches. Before treating this as a sigma-threading bug, the affected cell was re-run fresh in isolation.

**Context:** the rerun reproduced this plan's own value bit-for-bit (17 significant digits), ruling out run-to-run nondeterminism within this environment. The pattern (only `small_angle`'s near-zero-theta regime, only non-chunked code paths; weight1 -- using identical sigma-threading code -- matched perfectly) pointed to a deterministic but environment-dependent floating-point summation-order difference (e.g. BLAS/numpy version or thread-count) between when Phase 17's original CSV was generated and now, not a logic error in the sigma-threading plumbing.
**Source:** 17.1-04-SUMMARY.md "Issues Encountered" item 2

---

### Stage files individually and re-verify `git status --short` immediately before each commit when concurrent session activity is suspected
During Plan 17.1-01's execution, files unrelated to its scope (`gradient_variance_sweep.py`, `trainability/sweep.py`, `trainability/target_grid.py`, `tests/test_sweep.py`, a temp CSV) appeared, disappeared, and changed content between shell calls -- evidence of another concurrent session doing TRAIN-09-adjacent work in the same working tree.

**Context:** handled by never using `git add -A`/`git add .`, staging only the two files this plan actually owned, and re-checking `git status --short` right before each commit. No files belonging to the other in-flight work were touched, staged, or committed.
**Source:** 17.1-01-SUMMARY.md "Issues Encountered"

## Patterns

### Optional keyword parameter with the old hardcoded value as default -- safe retrofit onto an already-shipped pipeline
Both `sigma` (Plan 17.1-02) and `scale_factor` (Plan 17.1-03) were added as `param: float = OLD_CONSTANT` on `pooled_gradients_for_cell`/`run_gradient_variance_sweep`, threaded through every call site, with the default proven bit-identical to the pre-existing hardcoded behavior via an explicit test (not just assumed "obviously equivalent").

**When to use:** retrofitting a new dimension/hyperparameter onto a pipeline whose existing callers (tests, already-shipped CSVs) must keep producing bit-identical results. Never make the new parameter required.
**Source:** 17.1-02-SUMMARY.md "tech-stack.patterns"; 17.1-03-SUMMARY.md "tech-stack.patterns"

---

### Embed any per-cell parameter that varies chunk-to-chunk directly in the chunk filename
Established for `sigma` in Plan 17.1-02: any hyperparameter that a chunked long-running sweep depends on, but that isn't itself stored in the chunk's data file, must be part of the chunk filename (and the combine-step's glob pattern) so a mismatched invocation fails structurally (`FileNotFoundError`) rather than silently pooling incompatible data.

**When to use:** any future new per-cell scalar hyperparameter added to a chunked/resumable sweep pipeline in this project.
**Source:** 17.1-02-SUMMARY.md "patterns-established"

---

### Deterministic (no-randomness) init/config schemes are computed once per cell, outside the per-draw loop
Because `data_dependent`'s thetas are identical on every draw (no RNG substream), they're computed once per `(n, generator_scope)` cell before the draw loop begins, rather than re-dispatched inside the loop for no reason.

**When to use:** any future deterministic init/config scheme added alongside genuinely-random schemes in this sweep pipeline -- avoids wasted recomputation and keeps the "no random component" property visible in the code structure itself.
**Source:** 17.1-03-SUMMARY.md "tech-stack.patterns", "patterns-established"

---

### New sibling analysis script for follow-up work, reusing the canonical statistical primitive unmodified
`trainability_analysis_1701.py` follows `trainability_analysis.py`'s existing structure (`load_series` -> `fit_and_compare` -> `save_summary_csv`/`save_plot`) but as a genuinely separate script with its own CSV paths and constants, importing `trainability/curve_fit.py::fit_and_compare` directly and unchanged.

**When to use:** any future follow-up analysis against an already-shipped phase's canonical script -- create a new sibling script that reuses the shared statistical primitive, rather than extending or modifying the original output-generator a downstream doc already cites.
**Source:** 17.1-05-SUMMARY.md "patterns-established"

This entire investigation was structured as phase `17.1` -- a new phase directory depending on Phase 17's shipped artifacts -- rather than reopening Phase 17 itself, which had already been verified and shipped.

**When to use:** when new literature-motivated questions arise about an already-verified, already-shipped phase's results and the answer requires new sweeps/analysis rather than a correction to what shipped -- insert a decimal phase that depends on the original phase's artifacts and folds its findings into the same canonical doc as clearly-scoped new sections, leaving the original phase's content and verdict untouched.

## Surprises

### Phase 17's exponential-decay signature is NOT robust to kernel bandwidth
`weight1/uniform` and `mixed/uniform`'s original "exp" verdict survives only near sigma in `{0.03, 0.1}` (Phase 17's original bandwidth), flips to "inconclusive" at sigma in `{0.3, 1.0}` for both scopes, and then non-monotonically re-emerges as "exp" at sigma in `{3.0, 9.0}` for `weight1` only (`mixed` stays "inconclusive" through the top of the grid).

**Impact:** this is the phase's headline finding -- the original exp-decay signature is at least partly a fixed-bandwidth artifact, and the non-monotonic re-emergence means it can't be smoothed into a simple "signature fades with sigma" narrative. Explicitly reported as-is in docs/trainability-study.md rather than softened.
**Source:** 17.1-05-SUMMARY.md "Next Phase Readiness"; 17.1-06-SUMMARY.md "Accomplishments"

---

### Data-dependent init did not resolve the inconclusive verdict in either generator scope
TRAIN-10's literature-sourced (Recio-Armengol et al.) data-dependent init produced `weight1/data_dependent` and `mixed/data_dependent` verdicts that both remained "inconclusive" -- no clearer signal than `small_angle`'s original inconclusive result.

**Impact:** a genuine negative result for the alternative-init hypothesis, reported as measured rather than reframed as a partial success.
**Source:** 17.1-05-SUMMARY.md "Next Phase Readiness"; 17.1-VERIFICATION.md truth #4

---

### sigma=0.1 consistency check found a small but real floating-point discrepancy isolated to one specific (scope, init_scheme) combination
The plan expected exact bit-for-bit reproduction of Phase 17's original CSVs at sigma=0.1. weight1 matched exactly on all 10 compared rows, but `mixed/small_angle` at n=2,3,4 (6 of 8 mixed rows) differed by ~1e-13 to 1e-16 relative magnitude -- while `mixed/uniform` (using the identical code path) matched exactly, and `mixed`'s chunked n=5 rows also matched exactly.

**Impact:** narrowed to a deterministic, environment-dependent floating-point summation-order difference rather than a sigma-threading logic bug (ruled out by reproducing the discrepant value bit-for-bit on rerun). Had zero effect on the phase's headline finding since the survives/weakens/disappears classification only uses `uniform` cells, which matched exactly.
**Source:** 17.1-04-SUMMARY.md "Issues Encountered" item 2; 17.1-VERIFICATION.md "Anti-Patterns Found"

---

### TRAIN-10's sweep ran in ~40 seconds total, well under even the plan's own conservative "a few minutes" estimate
The research document predicted TRAIN-10 would be ~100x cheaper than TRAIN-09 due to deterministic init needing only `n_draws=1`; the actual run confirmed this even more dramatically than expected.

**Impact:** validated the research's cost-asymmetry finding as the single highest-leverage implementation-cost insight in the phase -- the entire TRAIN-10 dataset for both scopes was produced in under a minute, versus TRAIN-09's ~24-30 hours of wall-clock compute for the sigma-grid sweep.
**Source:** 17.1-05-SUMMARY.md "Issues Encountered", "Accomplishments"
