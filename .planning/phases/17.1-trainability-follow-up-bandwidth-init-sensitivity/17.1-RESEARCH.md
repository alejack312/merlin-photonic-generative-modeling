**Minimal-diff plan for both TRAIN-09 and TRAIN-10 (this is the concrete integration surface, not just a description of it):**

1. ### `trainability/target_grid.py` — bin-spacing verification (TRAIN-09's foundation)

`make_target_grid(n, lo=-0.1, hi=1.1)` builds `rows = 2**((n+1)//2)`, `cols = 2**(n//2)`, `xs = linspace(lo, hi, rows)`, `ys = linspace(lo, hi, cols)`. Because it's a regular axis-aligned grid, the nearest-neighbor spacing between adjacent bin centers is `min(dx, dy)` where `dx = (hi-lo)/(rows-1)`, `dy = (hi-lo)/(cols-1)` (or just `dx` when `cols==1`, i.e. `n=1`, which is out of this phase's CORE scope anyway). I computed this directly against the actual formula for every relevant `n`:

| n | rows | cols | dx | dy | bin spacing (min) |
|---|---|---|---|---|---|
| 2 | 2 | 2 | 1.2000 | 1.2000 | **1.2000** |
| 3 | 4 | 2 | 0.4000 | 1.2000 | **0.4000** |
| 4 | 4 | 4 | 0.4000 | 0.4000 | **0.4000** |
| 5 | 8 | 4 | 0.1714 | 0.4000 | **0.1714** |
| 6 | 8 | 8 | 0.1714 | 0.1714 | **0.1714** |
| 7 (stretch only, not CORE) | 16 | 8 | 0.0800 | 0.1714 | 0.0800 |
| 8 (stretch only, not CORE) | 16 | 16 | 0.0800 | 0.0800 | 0.0800 |

This exactly confirms the phase description's cited numbers (1.20 at n=2, 0.17 at n=5-6) and extends them to n=3,4 for the full CORE range. **CORE range only needs n=2..6** (weight1) / **n=2..5** (mixed) — the n=7/8 rows above are shown only for completeness/consistency-checking, not because TRAIN-09/10 need them (confirmed: ROADMAP.md's Phase 17.1 success criteria explicitly say "Phase 17's CORE n-range," and Phase 17's own STRETCH range was never reached/completed — see `docs/trainability-study.md`'s Honest max-n statement — so there is no STRETCH baseline for 17.1 to compare against even if it wanted to).

`gaussian_kernel_matrix_np` computes `K[a,b] = exp(-||center_a - center_b||^2 / (2*sigma^2))`. For ADJACENT bins (Euclidean distance = bin spacing computed above), the kernel value between adjacent bins is `exp(-spacing^2/(2*sigma^2))`. At Phase 17's fixed `SIGMA=0.1`:
- n=2: `exp(-1.2^2/(2*0.01)) = exp(-72) ≈ 0` (matches "≈0" cited in the phase description)
- n=5/6: `exp(-0.1714^2/(2*0.01)) = exp(-1.469) ≈ 0.230` (matches "≈0.23" cited in the phase description)

Both of these numbers I computed directly, confirming the mechanism description in the phase brief is accurate against current code — no need to re-derive it from scratch, only to implement the fix.

**Open design question the planner/owner must resolve explicitly (this is a genuine, non-mechanical decision, not a lookup):** "hold `sigma/bin-spacing` constant across n" requires picking WHICH ratio to hold constant — the ratio Phase 17 happened to have at n=2 (`0.1/1.2 ≈ 0.0833`, ⇒ sigma shrinks further at larger n than it already implicitly does, making the kernel MORE discriminating at large n than Phase 17's original run) or the ratio it happened to have at n=5-6 (`0.1/0.1714 ≈ 0.583`, ⇒ sigma grows at smaller n, making the kernel LESS discriminating at small n than Phase 17's original run), or some other reference point (e.g., anchor to whatever ratio the sibling literature paper's own median-heuristic bandwidth convention would imply — Recio-Armengol et al. Table 1, p.19, uses a median-heuristic-derived `σ3` alongside two Pauli-weight-targeted bandwidths, a genuinely different convention from a single fixed `σ`). I recommend anchoring to the SMALLEST n in the CORE range (n=2, ratio≈0.0833) as the reference — this preserves the "same magnitude sigma at the point where the fixed-bandwidth artifact is least severe" and makes the change at large-n as large/visible as possible (directly testing whether THAT'S what was driving the exponential-decay signature) — but this is a real modeling choice with a stated tradeoff, not a fact to look up, and per this project's CLAUDE.md ("no silent unilateral design decisions"), the plan must state this choice and its rationale explicitly rather than picking one silently. **Formula, once a reference n is picked:** `sigma(n) = SIGMA_ref * bin_spacing(n) / bin_spacing(n_ref)`.

## TRAIN-10's Primary Source: Recio-Armengol et al. (arXiv:2503.02934v2), Sec. 8.1.2, p.19

I read this section directly from the locally-available PDF (`docs/papers/2503.02934v2 (3).pdf`, page 19 of 50) rather than relying on `docs/iqp-baseline.md`'s existing summary — confirmed the summary is accurate, and extracted additional detail (the free hyperparameter's literature-tested range) not previously captured anywhere in this repo's docs. Verbatim recipe (Sec. 8.1.2, "Data-dependent parameter initialisation"):

> "for single qubit gates with X generator acting on qubit j, we initialize parameters to values `arcsin(sqrt(⟨x_j⟩))`, where `⟨x_j⟩` is the mean value of the jth dimension of the training data. This choice ensures that if all other parameters are set to zero, the model is equivalent to a product distribution with the same single qubit marginal distributions as the training data. Parameters of two-qubit gates acting on qubits j, k are initialized proportional to the covariance between the jth and kth dimensions of the training data (**the specific constant of proportionality is left as a free hyperparameter**), where we convert the training data to ±1 values rather than binary. [...] All other parameters (if there are any) are initialized via independent zero-mean normal distributions, whose standard deviation is another hyperparameter."

Their own hyperparameter grid-search table (Table 2, p.21) searched the two-qubit-gate scale factor over **[0.0001, 1.0]** (the single-qubit/weight-1 rule has no free scale — it's fixed by the `arcsin(sqrt(...))` formula itself).

**Confidence: HIGH** — read directly from the primary source PDF at the cited page, not from secondhand notes or training-data recall.

### Translating this recipe onto THIS project's target representation (the genuinely non-trivial step)

The paper's "training data" is literally a dataset of length-`n` **bitstrings** (their circuits generate bitstrings directly matching a bitstring dataset — see p.17-18's six datasets, all bitstring-valued). **This project's training data is NOT a bitstring dataset** — it's 400 continuous 2D `(x,y)` points from `make_circles()` (`generator/data.py::load_circles_data`), which Phase 17's own target-grid machinery (`trainability/target_grid.py::make_target_grid`) converts into `p_real`, a probability distribution over `2^n` GRID BINS (each bin identified with an n-bit index via `bin_index_fn(bitstring) = int(bitstring, 2)`). There is no direct "mean of the jth dimension of the training data" to read off — `⟨x_j⟩` must instead be defined as the marginal probability that **bit j of the sampled bin index equals 1, under `p_real`**, which is the natural and (I believe) intended translation, since `p_real` is exactly this project's stand-in for "the training data" in bitstring-generation terms (Phase 17's whole methodology treats `p_real` as the target the circuit's own bitstring-valued output distribution `q_dist` is trained/measured against).

**Concretely, given `p_real` (shape `(2**n,)`, from `target_grid.make_target_grid(n)`) and confirmed bit-ordering (`iqp_photonic_encoding.py::fock_to_bitstring` produces bitstring characters where `bitstring[k]` corresponds to qubit `k`/`thetas[k]`, in left-to-right order, and `bin_index_fn` treats that same left-to-right string as a standard MSB-first binary integer, i.e. `bit_k(b) = (b >> (n-1-k)) & 1` for bin index `b`):**

```python
def bit_k(bin_index: int, k: int, n: int) -> int:
    return (bin_index >> (n - 1 - k)) & 1

def empirical_mean_bit(p_real, k, n):
    # <x_k> = P(bit k == 1) under p_real
    idx = np.arange(2**n)
    bits_k = (idx >> (n - 1 - k)) & 1
    return float(np.sum(p_real * bits_k))

def weight1_data_dependent_theta(p_real, n):
    return [np.arcsin(np.sqrt(empirical_mean_bit(p_real, k, n))) for k in range(n)]

def empirical_pm1_covariance(p_real, j, k, n):
    idx = np.arange(2**n)
    zj = 2 * ((idx >> (n - 1 - j)) & 1) - 1   # {0,1} -> {-1,+1}
    zk = 2 * ((idx >> (n - 1 - k)) & 1) - 1
    return float(np.sum(p_real * zj * zk) - np.sum(p_real * zj) * np.sum(p_real * zk))

def weight2_data_dependent_theta(p_real, i, j, n, scale_factor):
    return scale_factor * empirical_pm1_covariance(p_real, i, j, n)
```

This is fully deterministic given `(n, weight2_pair)` and the chosen `scale_factor` hyperparameter — confirming the "no RNG substream needed" finding above. **`scale_factor` (the paper's free hyperparameter) is an owner decision, not something this research can resolve** — the paper searched `[0.0001, 1.0]` empirically; a defensible default for this project (untested, offered only as a starting point) would be `1.0` (their table's upper bound, and the value that makes weight-2 angles directly equal to the raw covariance) or a value chosen to keep weight-2 angles in a comparable numeric range to weight-1's (which are bounded in `[0, π/2]` by `arcsin`) — this needs to be stated explicitly in the plan per this project's "no silent unilateral design decisions" convention, not picked silently by whoever implements it.

**One more paper-fidelity note the plan should carry forward, not smooth over:** the paper's `⟨x_j⟩` is a probability in `[0,1]` by construction (binary data), matching `arcsin(sqrt(...))`'s valid domain `[0,1]`. This project's translation (`bit-marginal-of-p_real`) is also guaranteed in `[0,1]` for the same reason (it's a probability), so `arcsin(sqrt(...))` is well-defined for every `n` and every bit position — no edge-case guard needed here.

## Verdict Semantics — what "survives / weakens / disappears" and "non-inconclusive" mean operationally

Both phrases map directly onto `trainability/curve_fit.py::fit_and_compare`'s existing three-way `verdict` (`"exp"` / `"poly"` / `"inconclusive"`) and its `exp`/`poly` `r2`/`aic` sub-dicts — no new statistical machinery is needed, only a direct-comparison table between Phase 17's original 4 CORE verdicts and TRAIN-09/10's new verdicts:

- **"Survives"** = the SAME `(generator_scope, init_scheme)` cell's verdict stays `"exp"` (with `b>0`, i.e. genuinely decaying — `trainability_analysis.py::fit_verdict_to_plateau_label` already implements exactly this distinction) under the new sigma schedule/init scheme.
- **"Weakens"** = verdict stays `"exp"` but R²/delta-AIC margin shrinks materially, OR the fitted decay rate `b` shrinks materially (Phase 17's own `docs/trainability-study.md` already has precedent for reporting exactly this kind of nuance — see its "fit-quality caveat" and "Follow-up experiments" sections, which report near-degenerate `a`/`c` pairs and bootstrap CIs on `b` rather than just the verdict label).
- **"Disappears"** = verdict flips from `"exp"` to `"poly"` or `"inconclusive"`.
- **"Non-inconclusive" (TRAIN-10's specific bar, since `small_angle`'s ORIGINAL verdict was `"inconclusive"` for both `weight1` and `mixed`)** = TRAIN-10's new verdict is `"exp"` OR `"poly"` (either counts as a clearer result than `"inconclusive"` — ROADMAP.md success criterion 4 explicitly asks "whether it produces a clearer (non-inconclusive) verdict... and if so which direction," i.e. both directions are valid outcomes to report, not just an exp-decay finding).

**Concretely, the planner should build:** a comparison table (4 TRAIN-09 cells: weight1/uniform, weight1/small_angle-or-whichever-init-TRAIN-09-uses [see below], mixed/uniform, mixed/small_angle; 2 TRAIN-10 cells: weight1/data_dependent, mixed/data_dependent) with columns `{original_verdict, new_verdict, original_exp_r2/aic, new_exp_r2/aic, original_poly_r2/aic, new_poly_r2/aic, survives/weakens/disappears-or-clearer/still-inconclusive}` — this table (or its equivalent) is the literal deliverable that makes ROADMAP.md's success criteria 2 and 4 checkable, and is exactly the shape `docs/trainability-study.md`'s existing "Cross-reference verdict" and "Comparison against this phase's own CORE verdict" tables already use as a precedent/template (see that doc's existing structure below).

**Note on TRAIN-09's scope, worth flagging explicitly to the plan:** ROADMAP.md's success criteria 1-2 name specifically `weight1/uniform` and `mixed/uniform` as the cells whose exp-decay verdict is being tested for bandwidth-artifact sensitivity ("whether the exponential-decay verdict for `weight1/uniform` and `mixed/uniform` survives... weakens... or disappears") — these are the only two cells that had a definite `"exp"` verdict in Phase 17's original CORE data (`small_angle` was `"inconclusive"` for both scopes, so there's no exp-decay signature there to test for survival). Whether TRAIN-09 should ALSO re-run `small_angle` (for completeness/consistency with TRAIN-09's "both init schemes" phrasing elsewhere in the same success-criteria block) or only `uniform` (matching the specific verdict-survival question) is a scope question the plan should resolve explicitly — ROADMAP.md's own success criterion 1 says "both init schemes," so the safer reading is: run TRAIN-09's new-sigma sweep for BOTH `small_angle` and `uniform`, but frame the ANALYSIS (survives/weakens/disappears) around the `uniform` cells specifically, since only those had a signature to test.

- **No new MemoryError risk category is expected** — TRAIN-09 doesn't change circuit evaluation cost at all (only the kernel/sigma, which is downstream numpy arithmetic on an already-materialized `(2^n, 2)` centers array); TRAIN-10, if `n_draws` is reduced as recommended, does STRICTLY FEWER circuit evaluations than Phase 17's original sweep, not more. ## Common Pitfalls

### Pitfall 1: Silently changing Phase 17's own default sigma behavior
**What goes wrong:** if `sigma` is added as a required (non-defaulted) parameter to `pooled_gradients_for_cell`/`run_gradient_variance_sweep`, every existing call site (including Phase 17's own tests, `tests/test_sweep.py`) breaks.
**Why it happens:** natural refactor instinct to "just add the parameter."
**How to avoid:** default `sigma: float = SIGMA` (the existing module constant), so Phase 17's zero-argument-changed callers keep working bit-identically.
**Warning signs:** any existing test in `tests/test_sweep.py` failing after this change is a signal the default wasn't preserved correctly.

### Pitfall 2: Combining draw-chunks computed at different sigma values (TRAIN-09-specific)
**What goes wrong:** `combine_chunks` in `gradient_variance_sweep.py` re-derives `n_tracked` by calling `pooled_gradients_for_cell(..., draw_count=0, ...)` again — if this re-derivation call and the original `run_chunk` calls used different `sigma` values (e.g. sigma computed inconsistently between two separate CLI invocations), the combined result would silently mix or mis-summarize gradients computed under different kernels, and the code has no structural guard against this (sigma isn't stored in the `.npy` chunk files, only raw gradients are).
**Why it happens:** sigma is new plumbing being retrofitted onto chunking logic that was never designed to carry a second per-cell parameter beyond `(n, generator_scope, init_scheme, draw range)`.
**How to avoid:** either (a) make `sigma` part of the chunk filename (like `n`/`init_scheme`/draw-range already are, via `_chunk_path`) so a mismatched sigma produces a clean "no matching chunk files found" error rather than a silent semantic mismatch, or (b) require `--sigma` to be re-specified identically at both `run_chunk` and `combine_chunks` invocation and validate/log it plainly. Only relevant if TRAIN-09 actually needs draw-chunking (likely only for the same n=5-mixed cell Phase 17 already needed it for).
**Warning signs:** a combined CSV row whose implied kernel doesn't match either chunk's stated sigma, or (more subtly) a TRAIN-09 result that looks anomalously similar to Phase 17's original SIGMA=0.1 result at a large n where the two sigmas should differ a lot.

### Pitfall 3: Getting the bitstring-index-to-qubit-index bit-ordering backwards for TRAIN-10
**What goes wrong:** `bin_index_fn(bitstring) = int(bitstring, 2)` treats `bitstring[0]` (leftmost char) as the MOST significant bit. `fock_to_bitstring` (in `iqp_photonic_encoding.py`) builds that string left-to-right in qubit order (qubit 0's mode pair first). Getting this backwards (e.g. treating bin-index bit 0 as the LEAST significant bit, or as qubit `n-1` instead of qubit `0`) would silently apply each weight-1 data-dependent angle to the WRONG qubit — the sweep would still run and produce numbers, with no error, just an incorrect init.
**Why it happens:** binary-string-to-integer conventions (MSB-first vs LSB-first) are a classic silent-bug source, and this project's own `bin_index_fn` docstring calls the mapping "arbitrary" (chosen for a different reason — bin-index-to-grid-position, not qubit-to-bit correspondence) without spelling out the MSB/LSB implication for a NEW consumer like TRAIN-10.
**How to avoid:** use the exact bit-extraction formula verified in this research (`bit_k(bin_index, k, n) = (bin_index >> (n-1-k)) & 1`), and add a small unit test asserting `bit_k` extracted from a KNOWN bitstring (e.g. `bin_index_fn("0" * (n-1) + "1")` should have `bit_k(..., n-1, n) == 1` and all other `bit_k(...) == 0`) round-trips correctly before trusting any TRAIN-10 sweep output.
**Warning signs:** TRAIN-10's `weight1_data_dependent_theta` values look "reasonable" but a spot-check against `p_real`'s actual per-bit marginals (computed independently, e.g. via `np.sum(p_real.reshape(rows,cols), axis=...)`-style marginalization matched against the grid's own x/y structure) doesn't match.

## Open Questions

1. **Which sigma-ratio reference point should TRAIN-09 anchor to (n=2's ratio, n=5/6's ratio, or something else)?**
   - What we know: the mechanism and the exact bin-spacing numbers at every CORE n (table above).
   - What's unclear: which anchor point best answers "is the exp-decay signature a bandwidth artifact" — anchoring small (n=2's ratio) makes large-n MORE discriminating than Phase 17's original run; anchoring large (n=5/6's ratio) makes small-n LESS discriminating. Either is defensible; they test slightly different things.
   - Recommendation: state this explicitly as an owner decision in the plan (per CLAUDE.md's "no silent unilateral design decisions"), with n=2-anchoring as the suggested default given the rationale above, but do not lock it in without the owner's sign-off.

2. **What value should TRAIN-10's weight-2 scale-factor hyperparameter take?**
   - What we know: the paper leaves it fully free and searched `[0.0001, 1.0]` empirically across six very different datasets/circuit sizes (nothing directly comparable to this project's n=2-6, 2D-circles-derived target).
   - What's unclear: no principled default transfers cleanly to this project's much smaller n-range and different target distribution.
   - Recommendation: pick one fixed, stated value (e.g. 1.0) for the CORE sweep and note this is a single-value spot-check, not a hyperparameter sweep — TRAIN-10's success criteria only ask for ONE new init scheme's result, not a scale-factor sweep, so over-scoping this would be a MoSCoW violation (out of stated scope) — but the plan should still state the chosen value and a one-line reason, not leave it implicit in code.

3. **Should `n_draws` shrink for TRAIN-10 given its deterministic init?**
   - What we know: the recipe (weight-1 `arcsin(sqrt(mean))`, weight-2 `scale_factor * covariance`) has no random component, so 100 draws would produce 100 bit-identical theta vectors.
   - What's unclear: whether the owner wants to keep `n_draws=100` anyway for output-shape/summary-code uniformity with TRAIN-09's cells (simpler comparison table, marginal extra compute cost is small relative to Phase 17's original ~950s-per-cell-at-n=6 profile) or exploit the ~100x cost savings.
   - Recommendation: flag explicitly to the owner during planning; either choice is defensible, but shouldn't be decided silently by whoever writes the plan.
