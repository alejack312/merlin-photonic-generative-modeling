## Decisions Made
- **Retry-single-cell-on-MemoryError, don't restart the whole invocation.** When a `(n, init_scheme, sigma)` cell hit Perceval's transient `MemoryError: bad allocation` (weight1's n=6 cells, ~50% of the time; one mixed n=5 chunk, once), the fix was to retry only that specific missing cell/chunk once memory was confirmed released (via `Get-CimInstance Win32_OperatingSystem` free-memory checks going from ~800MB-1.3GB during failure back to 6-7GB after). This is a direct application of the plan's own resumability design (every row/chunk is flushed+fsynced immediately, so nothing already-written is ever lost) rather than a new mechanism.
- **Task 3's exact-equality check is reported as a partial/near-match, not forced to PASS.** The plan's verification criterion states the check should pass "exactly" for every row, and that a failure means "something is wrong with the sigma-threading plumbing (Plan 17.1-02/17.1-03), not with the data." Given the evidence gathered (see Issues Encountered), a real sigma-threading bug is very unlikely -- but declaring an unambiguous PASS despite 6 rows technically failing the literal bit-for-bit bar would misrepresent the check's output. This project's CLAUDE.md is explicit that result interpretation is the owner's job, not something to smooth over -- so the raw comparison, the diagnostic work done to characterize it, and an honest FAIL-against-literal-criterion verdict are all recorded here for the owner to weigh.

## Issues Encountered

**1. Transient `MemoryError: bad allocation` inside Perceval's `Analyzer.compute()`, recurring throughout execution.**
- **Pattern:** weight1's n=6 cells (the scope's known Fock-space-size ceiling) failed with this error on the first attempt roughly half the time, across all 6 sigma values (8 of 16 total n=6 invocations needed exactly one retry; none needed more than one). Mixed scope hit this exact-same error class exactly once, at sigma=3.0's uniform n=5 draw-chunk `[20,40)` -- inside `weight2_param_shift_delta` this time rather than the weight1 code path, but the identical `TypeError: 'NoneType' object is not subscriptable` -> `MemoryError: bad allocation` traceback shape.
- **Root cause:** This machine had materially lower free system memory during this execution window than during Phase 17's original CORE sweep (confirmed directly: free memory measured as low as ~800MB-1.3GB during a failing attempt, recovering to 6-7GB once the failing process exited) -- consistent with STATE.md's already-documented ~1GB-free-memory constraint, not a new or different failure mode.
- **Resolution:** Retried only the specific failed cell/chunk once memory was confirmed released. Every retry succeeded on the second attempt; no cell needed more than one retry across the entire 6-sigma-value grid for either scope. No already-written CSV rows were ever lost (the CLI's per-row flush+fsync, and per-chunk `.npy` files for the draw-chunked cells, made every retry a clean single-cell resume).
- **Safety note:** No OS-level process-management action was taken against any process this session did not itself start and track, per the standing safety rule from a prior incident (STATE.md). Free-memory checks were read-only system-state queries, not process inspection/manipulation.

**2. Task 3's sigma=0.1 consistency check does not achieve literal bit-for-bit equality for 6 of 18 compared rows (all in the mixed scope, all `small_angle` init, all at n=2, 3, or 4).**
- **Full comparison result:**
  - weight1 (10 rows compared: n=2..6 x 2 init schemes): **all 10 match exactly** (`mean`, `var`, `std`, `median`, `abs_mean`, `rms`, `n_samples` bit-identical).
  - mixed (8 rows compared: n=2..5 x 2 init schemes): **2 of 8 match exactly** (both `n=5` rows, `small_angle` and `uniform`). The other 6 (`small_angle` at n=2, n=3, n=4; and interestingly `uniform` at n=2, n=3, n=4 all matched too -- only `small_angle` at n=2, 3, 4 mismatched) differ from Phase 17's original values at the last 1-3 significant digits of a 16-17 digit double -- e.g. `mean` for n=2/small_angle: this run's `-0.0073057767953655815` vs. Phase 17's original `-0.00730577679536554`, a relative difference of order 1e-15.
- **Diagnostic work done (not just asserted):** re-ran the affected `mixed n=2 small_angle sigma=0.1` cell fresh in isolation. The rerun reproduced this plan's own sweep value **bit-for-bit exactly** (`-0.0073057767953655815`, identical to 17 significant digits), and differed from Phase 17's original value by the same ~1e-15 relative amount. This rules out run-to-run nondeterminism (e.g. thread-scheduling-dependent floating-point summation order varying between invocations) as the direct cause within this execution -- whatever produces the small_angle/n<=4 discrepancy is itself deterministic and reproducible under the current environment; it just doesn't match Phase 17's original environment/run bit-for-bit.
- **Assessment (not a final interpretation -- offered as diagnostic input for the owner):** the magnitude (~1e-13 to 1e-16 relative) is at the noise floor of IEEE double-precision arithmetic, and the pattern -- affects only `small_angle`'s near-zero-theta regime (where interference amplitudes are closest to cancellation, amplifying relative floating-point noise) and only the non-chunked n=2/3/4 code path (weight1 has no chunking at all and matched perfectly across the board; mixed n=5 uses draw-chunking in both the original and this run and matched perfectly) -- is consistent with a deterministic but environment-dependent floating-point summation-order difference (e.g. a BLAS/numpy library version or thread-count difference between when Phase 17's original CSV was generated and now), not with a logic error in the sigma-threading plumbing itself (Plans 17.1-02/17.1-03). If the sigma-threading code itself were wrong, weight1 (using the identical threading code) would be expected to show the same kind of drift, and it does not -- it matches perfectly.
- **Per this project's CLAUDE.md ("Interpreting benchmark/metric results ... the owner writes the interpretation first, Claude checks it"):** this finding is reported as raw fact plus diagnostic evidence, not as a final verdict. The literal plan criterion ("passes exactly for every row") is **not met** for 6 of 18 rows; the practical significance of that miss (almost certainly nil, given the evidence above) is left to the owner's judgment.
