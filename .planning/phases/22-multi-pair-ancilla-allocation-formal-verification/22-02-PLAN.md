Create `results/phase22_allocation_invariant.md`. It is prose plus arithmetic — no Forge code, and no `.frg` file may be created by this plan. It must contain these sections, in this order:

`## Compatibility rule.` State precisely: two pairs `(i,j)` and `(i',j')` may be assigned the same ancilla block if and only if `{i,j} ∩ {i',j'} = ∅` (vertex-disjointness). State why vertex-sharing pairs cannot pool: diagonal ZZ terms on overlapping qubits commute and both legitimately apply in a multi-ZZ IQP circuit, so vertex-sharing pairs are simultaneously active and cannot be treated as mutually exclusive. Flag that this rule is Claude's Discretion under `22-CONTEXT.md` and is put to the owner for confirmation at Plan 22-03's checkpoint.

`## Allocation concretization: round-robin edge-colouring of K_n.` State the concrete, fixed, subset-independent formula — an allocation that is a pure function of a pair's own `(i,j)` and does NOT depend on which other pairs are active (this condition is what the pairwise reduction below depends on, so it must be stated as a condition, not assumed):
- Odd `n`: `colour(i,j) = (i + j) mod n`, using `K = n` blocks.
- Even `n`: let `m = n - 1` (odd). For `i, j < m`: `colour(i,j) = (i + j) mod m`. For the last vertex: `colour(i, n-1) = (2i) mod m`. Using `K = m = n - 1` blocks.
State the standard construction argument for why the even case is proper: under `(i+j) mod m` on `K_m` with `m` odd, colour class `c` is a near-perfect matching missing exactly the single vertex `v` with `2v ≡ c (mod m)` (unique because `m` is odd), and attaching vertex `n-1` to that missed vertex with colour `c` completes each class to a perfect matching.
State plainly, per `22-CONTEXT.md` D-05's honesty caveat: the chromatic index of `K_n` is a KNOWN theorem (`n-1` for even `n`, `n` for odd `n`, Koenig/Vizing). This formula constructively realizes known combinatorics; it does not settle an open problem.

`## Mode-index formula.` A pair assigned block `c` occupies ancilla modes `2n + 4c`, `2n + 4c + 1`, `2n + 4c + 2`, `2n + 4c + 3`. State that this generalizes `_build_weight2_cp_processor_no_postselect`'s single-pair tail-ancilla dict (`{2n:4, 2n+1:5, 2n+2:6, 2n+3:7}`, i.e. the `c = 0` case) rather than replacing it, and that the total mode count becomes `2n + 4K` instead of `4 * C(n,2)` under contiguous allocation — the sub-linear-in-k growth D-02 selected pooling to obtain. Give the concrete comparison at `n = 8`: pooled `2*8 + 4*7 = 44` modes versus contiguous `2*8 + 4*28 = 128` modes.

`## Bitwidth justification.` Compute the largest value the model computes, explicitly, and justify the Forge bitwidth against it — matching `forge/ancilla_mapping.frg`'s existing header-note discipline. At `n = 8` (even), `K = n - 1 = 7`, so `c_max = 6` and the largest mode index is `2*8 + 4*6 + 3 = 43`. State that `for N Int` is a BITWIDTH, not a count, so `for 6 Int` gives the signed range `[-32, 31]` and would SILENTLY overflow at 43 — Forge does not error on this. The minimum safe bitwidth is `for 7 Int` (range `[-64, 63]`). Note explicitly that `22-RESEARCH.md`'s own code snippets still show `for 6 Int` and are internally inconsistent with the finding in that same section, and that `for 6 Int` must NOT be copied forward from `ancilla_mapping.frg` (where the maximum was only 19).

`## The invariant.` State what the property quantifies over: `n` from 2 to 8 inclusive; all `C(n,2)` pairs `(i,j)` with `0 <= i < j < n`; the block assignment `colour: Pair -> [0, K)`; and the data-port range `0 .. 2n-1`. State the two conjuncts: (a) no two vertex-sharing pairs are assigned the same block; (b) no ancilla mode index `2n + 4c + t` for `t` in `0..3` equals any data port in `0 .. 2n-1`. State what a counterexample looks like AS A STRUCTURE, not as a number: a specific `n`, a specific pair of pairs sharing a qubit index, and the specific block index both were assigned — i.e. an exhibited colliding configuration, not a failing arithmetic comparison.

`## Pairwise-reduction argument.` This is the load-bearing step and must be written out in full, because it is what licenses not literally enumerating the `2^28` subsets the original framing worried about. The argument: collision is a BINARY predicate — it only ever relates two pairs at a time, with no three-or-more-way interaction (unlike a capacity constraint, where three simultaneously-active items can jointly violate something no two of them violate alone). Therefore, PROVIDED the block assignment is a pure function of each pair's own identity and does not depend on which other pairs are active, "no collision over every subset of simultaneously-active pairs" is EXACTLY EQUIVALENT — not weaker — to "no collision over every pair of pairs". Forward direction: if a subset `S` collides, the collision is witnessed by two elements of `S`, so a pairwise counterexample exists. Converse: a colliding pair of pairs is itself a two-element subset. State the count this collapses to at `n = 8`: `C(28,2) + 28 = 406` cases. State explicitly that the reduction is UNSOUND for a dynamic/adaptive allocation (greedy first-fit recomputed per active set), which is precisely why the fixed formula above was chosen, and that adding any non-pairwise invariant later (e.g. a global ancilla-budget cap) would break the reduction and force genuine subset quantification.

`## What the Forge model will actually ask.` Per D-05, the model poses a SEARCH question, not a verification one: "does an assignment of at most `K` ancilla blocks to all `C(n,2)` pairs exist such that no two vertex-sharing pairs collide, and what is the minimum such `K`?" State why: verifying a given fixed colouring reduces to the 406 pairwise checks above and is trivially brute-forceable, which would drive MPAIR-05 to a second "Forge did not earn its place" verdict by construction; FINDING a minimum colouring is constraint satisfaction, which is what a SAT-backed model finder is for. State that the Forge model must therefore NOT encode the round-robin formula — it searches over all block assignments freely, and the round-robin formula is the independently-constructed witness whose colour count must agree with Forge's found minimum.

`## Scope boundary — what this does NOT establish.` State explicitly and without softening: this invariant is about ancilla mode INDEX bookkeeping only. Index-level non-collision does NOT establish that reusing those physical modes across sequentially-composed CP(alpha) unitaries reproduces the same physics as dedicated per-pair ancilla. That is a separate, independently necessary condition, it is a unitarity/physics claim categorically outside what a bounded model finder can check (the same tool-category boundary `16-CONTEXT.md` drew around Forge), and it was settled separately by MPAIR-07 — cite `results/phase22_reuse_gate.md` and its owner ruling by name. Any write-up language implying the Forge check "proves pooling is safe" rather than "proves the chosen index-allocation scheme does not collide" is wrong.
