# Phase 17: Trainability / Barren-Plateau Study - Research

**Researched:** 2026-08-09
**Domain:** Parameter-shift differentiation of a Perceval photonic-Fock-space simulation; MMD²-based gradient-variance / barren-plateau measurement; poly-vs-exponential curve fitting
**Confidence:** HIGH on gate mechanics and measured compute costs (self-derived, numerically verified, and directly benchmarked in this repo's venv); MEDIUM on the MMD²-target bin-mapping design (inferred, not yet implemented anywhere in this repo); MEDIUM on curve-fit methodology (sibling project's pattern is real but doesn't fully satisfy TRAIN-02 as shipped).

## Summary

Phase 17 needs three new pieces of code, all built fresh (the sibling project's autodiff/analytic-cosine gradient machinery does not transfer): (1) a parameter-shift gradient for the `WP(θ,0)` phase gate that realizes each weight-1 (and, additively, weight-2-fold) generator, (2) an MMD² loss and its gradient defined directly on the *exact* output distributions `photonic_iqp_distribution`/`photonic_weight2_iqp_distribution` already return, and (3) a poly-vs-exponential model-comparison routine over the resulting gradient-variance-vs-n data.

The most consequential finding is about compute cost, not math: this repo's `WP(θ,0)` gate is generated by `Z` (eigenvalues ±1), so the correct parameter-shift rule is `∂f/∂θ = f(θ+π/4) − f(θ−π/4)` with **no division** — shifting by the textbook `π/2` instead (the value correct for the `exp(-iθZ/2)` convention, not this repo's `exp(iθZ)` convention) lands exactly on a zero of `sin(2s)` and silently produces a garbage (0/0 or wildly wrong) gradient. Separately, and more decisively for planning: `photonic_iqp_distribution`/`photonic_weight2_iqp_distribution` compute the full Perceval Fock-space distribution by enumerating every photon-number-conserving output state across `2n` (or `2n+2`) modes — a combinatorial space of size `C(3n-1,n)` (weight-1) or `C(3n+3,n+2)` (weight-2), not `2^n`. I benchmarked this directly in this repo's venv: weight-1 goes from 0.19s (n=5) to 247s (n=8) for a *single* distribution call; weight-2 goes from 4.9s (n=5) to 71s (n=6). With the ≥100-draws × 2-shifts-per-tracked-parameter cost structure TRAIN-01 requires, this puts the realistically reachable ceiling for this project at roughly n=7-8 for weight-1-only and n=5-6 for mixed — far short of the N=20-24 literature threshold TRAIN-08 asks the sweep to reach toward. That gap is real and should be reported honestly, not engineered away by silently switching to the mathematically-equivalent-but-forbidden closed-form shortcut.

**Primary recommendation:** implement gradients as `dq/dθ_k = photonic_iqp_distribution(n, θ+π/4·e_k) − photonic_iqp_distribution(n, θ−π/4·e_k)` (exact, elementwise, per output bitstring), combine with the already-implemented quadratic-form MMD² (`generator/mmd.py`'s `p@K@p + q@K@q − 2p@K@q`) via `∂MMD²/∂θ_k = 2(q−p)ᵀK·(dq/dθ_k)`, cap the number of tracked parameter indices per setting (3-5, mirroring the sibling project's `min(5, actual_m)` convention) to keep the ≥100-draw floor affordable, and plan the n-sweep around measured per-n costs (n=2..7 comfortably, n=8 as an overnight stretch, n≥9 explicitly out of reach) rather than around the literature's n=20-24 target.

### Pattern 1: Two-term parameter-shift for a `WP(θ,0)`-generated gate
**What:** `WP(θ,0) = diag(e^{iθ}, e^{-iθ})` is `exp(iθZ)` — the generator `Z` has eigenvalues `{+1,-1}`, so every output probability `q_x(θ_k)` (holding other parameters fixed) is a sinusoid of frequency **2** in `θ_k`: `q_x(θ_k) = A_x cos(2θ_k+φ_x) + C_x`.

**Derivation (self-derived, numerically verified below):** for `f(θ)=A cos(2θ+φ)+C`,
`f(θ+s) − f(θ-s) = -2A sin(2θ+φ) sin(2s) = f'(θ) · sin(2s)`, so `f'(θ) = [f(θ+s)-f(θ-s)] / sin(2s)`. Choosing `s=π/4` makes `sin(2s)=1`:

```
∂f/∂θ = f(θ + π/4) − f(θ − π/4)          # exact, no division, no 1/2 factor
```

**Numerical check performed during this research** (closed form `P(H)=cos²θ` from `expected_single_qubit_probs`):
```
f(θ)=cos²θ  =>  f'(θ) = -sin(2θ)  (standard calculus)
f(θ+π/4) - f(θ-π/4) = cos²(θ+π/4) - cos²(θ-π/4)
                     = [1-sin(2θ)]/2 - [1+sin(2θ)]/2 = -sin(2θ)   ✓ exact match, all θ
```

**When to use:** every weight-1 `thetas[k]` parameter, in both `photonic_iqp_distribution` and (since the pi/4 fold in `photonic_weight2_iqp_distribution` is an *additive constant* on `thetas[i]`/`thetas[j]`, which shifts `φ_x` but not the frequency) `photonic_weight2_iqp_distribution`'s weight-1 parameters too.

**Critical pitfall this corrects:** the far more commonly-cited "shift by `π/2`, divide by 2" rule is for the *different* convention `U(θ)=exp(-iθG/2)` (e.g. PennyLane/Qiskit `RZ(θ)`), which has eigenvalue gap `1`, not `2`. Applying `s=π/2` to *this* repo's `exp(iθZ)` convention plugs into `sin(2s)=sin(π)=0` — a division by exactly zero. This is exactly the kind of silent-wrong-number risk this repo's CLAUDE.md and prior phases have flagged repeatedly (the `numpy.float64`/`StateVector` and ancilla-annotation pitfalls in STATE.md are the same genre of "looks-fine, is-actually-wrong" bug). **Verification step to include in the plan:** a unit test asserting the shift-rule gradient matches a finite-difference gradient of `expected_single_qubit_probs`/`expected_joint_distribution` (the closed form) to floating-point precision, analogous to `tests/test_iqp_photonic_encoding.py`'s existing closed-form-matching tests.

### Pattern 2: MMD² gradient via the chain rule through the exact distribution (not through amplitudes)
**What:** This repo's MMD² (`generator/mmd.py`) is `MMD²(p,q) = pᵀKp + qᵀKq − 2pᵀKq`, a scalar quadratic form in explicit probability vectors `p` (fixed target), `q(θ)` (circuit output), over a shared set of K bin centers, `K` = the Gaussian kernel matrix on those centers (Euclidean distance, **not** the sibling project's Hamming-distance/Boolean-Fourier formulation — see "Don't Hand-Roll" for why the sibling's gradient code does not transfer).

Standard quadratic-form calculus: `∂MMD²/∂q = 2K(q−p)`. Combined with Pattern 1's exact per-bin derivative `∂q_x/∂θ_k = q_x(θ+π/4·e_k) − q_x(θ−π/4·e_k)`:

```python
# q_theta, q_plus, q_minus are numpy arrays of shape (K,), built by mapping
# photonic_iqp_distribution(n, theta)'s {bitstring: prob} dict onto the same
# K bin indices p_real uses (see Open Questions: bin-mapping convention).
dq_dtheta_k = q_plus - q_minus                      # exact, Pattern 1
grad_k = 2.0 * (q_theta - p_real) @ kernel_matrix @ dq_dtheta_k
```

This requires exactly **2 calls** to `photonic_iqp_distribution` (or `photonic_weight2_iqp_distribution`) per tracked parameter per θ draw — the same "2 evals per param" cost structure as any parameter-shift scheme, independent of how large K is.

**Why this is exact, not an approximation, despite MMD² being *quartic* in the circuit's state amplitudes:** the parameter-shift rule is only guaranteed exact for a *linear* observable expectation value (`⟨ψ(θ)|M|ψ(θ)⟩` for fixed `M`) — and each `q_x(θ_k) = ⟨ψ(θ)|Πₓ|ψ(θ)⟩` (`Πₓ` = projector onto output `x`) *is* exactly such a quantity, individually, regardless of what nonlinear function of the full vector `q` is computed downstream. The chain rule through `MMD²(q(θ))` is exact as long as `∂q_x/∂θ_k` itself is exact — which Pattern 1 established it is. No Monte-Carlo variance enters this gradient at all (consistent with `docs/mmd-loss.md`'s note that this repo's MMD² is already an exact closed form with no sampling noise).

### Anti-Patterns to Avoid
- **Reusing `iqp_bp/mmd/gradients.py`'s `grad_expectation_analytic` line-for-line.** It differentiates the Van den Nest cosine-formula `⟨Z_a⟩` closed form — a qubit-side, Z-word-expectation object that has no counterpart in this project's photonic pipeline (this project's `q` is a raw probability vector, not a set of sampled Pauli-string expectation values). The *shape* of their code (estimate-gradient-variance-over-theta-seeds, cap tracked param count, split RNG substreams) is worth mirroring; the gradient *formula* is not.
- **Using `π/2` shift out of habit** from qubit-rotation-gate tutorials (see Pattern 1's pitfall).
- **Treating `photonic_iqp_distribution`'s per-call cost as `O(2^n)`.** It is not — see "Common Pitfalls" and the measured table below.

## Common Pitfalls

### Pitfall 1: Wrong parameter-shift value (π/2 vs π/4) — silent, not crashing
**What goes wrong:** using the standard-tutorial `π/2` shift on `WP(θ,0)` produces `sin(2·π/2)=sin(π)=0` in the denominator of the general shift formula — either a literal `ZeroDivisionError` if the formula is implemented with an explicit division, or, if implemented as the *unnormalized* two-point difference `f(θ+π/2)-f(θ-π/2)` without ever computing the correct denominator, a value that is coincidentally exactly **zero** for every θ (since `f(θ+π/2)-f(θ-π/2) = f'(θ)·sin(π) = 0`), producing an all-zero "gradient" that looks like a legitimate barren-plateau signal but is actually a shift-rule bug.
**Why it happens:** the `π/2`/divide-by-2 rule is memorized from `exp(-iθG/2)`-convention tutorials (Qiskit/PennyLane `RZ`); this repo's `WP(θ,0)=exp(iθZ)` uses the other convention.
**How to avoid:** use `s=π/4`, no division (Pattern 1). Add the closed-form-vs-shift-rule unit test described in Pattern 1.
**Warning signs:** every measured gradient is exactly 0.0 (not just small) across all θ draws — a real (not shift-rule-bug) barren plateau would still show tiny but nonzero, floating-point-noise-scale variance, not literal exact zero.

### Pitfall 2: Treating photonic distribution cost as polynomial/exponential in `n` the way qubit `2^n` is
**What goes wrong:** planning the n-sweep range (and time budget) by analogy to the sibling project's qubit-side `2^n` cost, which comfortably reaches n=20.
**Why it happens:** `photonic_iqp_distribution`/`photonic_weight2_iqp_distribution` call Perceval's `Analyzer(processor, [input_state], "*")`, which enumerates **every** photon-number-conserving Fock state across all `2n` (or `2n+2`) modes — a space of size `C(3n-1,n)` (weight-1) or `C(3n+3,n+2)` (weight-2), not `2^n`. This is much larger and grows faster than `2^n` (Stirling: `C(3n-1,n) ~ (27/4)^n/√n ≈ 6.75^n`, vs. qubit `2^n`).
**How to avoid:** budget the sweep from the measured numbers below, not from the qubit-side literature's reachable range.
**Warning signs:** a single `photonic_iqp_distribution(n, ...)` call taking minutes already at n=7-8 (measured, see table below) is a hard signal, not a fluke — it will only get worse per additional qubit, non-linearly.

**Measured costs (this repo's venv, `perceval-quandela==1.2.4`, single circuit-run per data point, random θ draws):**

| n | weight-1 `photonic_iqp_distribution` time | raw Fock dim `C(3n-1,n)` | weight-2 `photonic_weight2_iqp_distribution` time | raw Fock dim `C(3n+3,n+2)` |
|---|---|---|---|---|
| 2 | 0.033s | 10 | 0.041s | 126 |
| 3 | 0.013s | 56 | 0.055s | 792 |
| 4 | 0.033s | 330 | 0.378s | 5,005 |
| 5 | 0.186s | 2,002 | 4.864s | 31,824 |
| 6 | 1.543s | 12,376 | 70.901s | 203,490 |
| 7 | 18.386s | 77,520 | (not measured — extrapolated: several minutes) | 1,264,540 |
| 8 | 247.026s | 490,314 | (not measured — extrapolated: tens of minutes to hours) | ~7.7M |

(`valid_bitstrings` in every measured case was exactly `2^n`, and `residual`/`herald_failure_prob` matched the previously-established exact values (`0.0` residual, `~0.9259 = 1-2/27` herald failure) — confirms these timings are the real production code path, not a degenerate/broken run.)

**Full sweep-cost implication (the number that actually matters for planning):** TRAIN-01's ≥100-draws floor means each *tracked parameter* costs `100 draws × 2 shift evals` = 200 circuit-distribution calls. Capping tracked parameters per setting at ~5 (mirroring the sibling project's `min(5, actual_m)`) gives ~1000 circuit-distribution calls per `(n, init_scheme, generator_scope)` combination:
- n=6, weight-1: `1000 × 1.5s ≈ 25 min`. n=7: `1000 × 18.4s ≈ 5.1 hr`. n=8: `1000 × 247s ≈ 68.6 hr (~2.9 days)`.
- n=5, mixed: `1000 × 4.9s ≈ 82 min`. n=6, mixed: `1000 × 70.9s ≈ 19.7 hr`.
- Multiply by 2 for both init schemes (small-angle + uniform), and note weight-1's own growth rate is accelerating (each +1 in n multiplied the single-eval time by 8×, 12×, 13× at the last three measured steps) — n=9 is very unlikely to be reachable within a single-digit-day budget, and n=10+ is very unlikely to be reachable at all within this project's timeline.

**Recommendation for the sweep's n grid (research judgment, not a locked decision):** weight-1-only: `n ∈ {2,3,4,5,6,7}` as the reliable core (satisfies TRAIN-07's need for an `n≥6` data point against `docs/iqp-baseline.md`'s rule), `n=8` as an explicit overnight-scale stretch goal (consider reducing tracked-param-count or draw count further for n=8 specifically, or running only one init scheme, and reporting that reduction honestly per TRAIN-05). Mixed weight-1+weight-2: `n ∈ {2,3,4,5,6}` as the reliable core, `n=6` already at the edge of an overnight run. `n≥9` (weight-1) / `n≥7` (mixed) should be reported as "not reached, compute-bound" per TRAIN-05/TRAIN-08 rather than attempted — this is a substantially smaller ceiling than the qubit-side and literature's n=20-24, and that gap is itself part of the honest result TRAIN-05 asks for.

### Pitfall 3: Target-distribution K doesn't match the photonic circuit's `2^n` output space
**What goes wrong:** v1.0's existing target (`compute_p_real` over `natural_sorted_centers()`'s fixed K=462 grid) is sized for a *different* circuit (`ML.QuantumLayer.simple(input_size=10)`'s own Fock-state output width), not for this project's IQP bitstring space, which is `2^n` and changes at every sweep point.
**Why it happens:** CONTEXT.md's locked instruction to "start with v1.0's existing target" doesn't by itself resolve how a fixed 462-bin target lines up with a `2^n`-outcome circuit that must be re-run at n=2,3,4,...,7.
**How to avoid (recommended, not locked — flagged explicitly below in Open Questions):** generalize `make_natural_bin_centers`/`compute_p_real` to build a fresh `rows×cols` grid with `rows·cols = 2^n` at each sweep point (e.g. `rows=2^⌈n/2⌉, cols=2^⌊n/2⌋`), recomputing `p_real` from the same `load_circles_data()` circles dataset each time — this is a direct, mechanical generalization of the existing v1.0 machinery, not a new design.
**Warning signs:** any code that tries to hardcode K=462 while sweeping n, or that silently truncates/pads a `2^n`-length `q` vector to 462 bins.

### Pitfall 4: Assuming the exact-MMD²-vs-Monte-Carlo crossover matters here
**What goes wrong:** importing the sibling project's `n>20` exact-enumeration cap (`mmd2_exact_small_n`) as if it were the binding constraint for this project too.
**Why it happens:** the sibling's binding constraint is the `K×K` (`K=2^n`) kernel-matrix cost, which does become expensive by n~16-20. This project's binding constraint (Pitfall 2, above) makes the *photonic simulation itself* intractable by n~8-9 — several sweep points before the K×K kernel matrix (`K=2^8=256` → 256×256, trivial; even `K=2^12=4096` → 4096×4096×8 bytes ≈ 128MB, still fine) would become the bottleneck.
**How to avoid:** given the measured Perceval costs above, the exact-MMD² path (mirroring `mmd2_exact_small_n`, no Monte Carlo) can almost certainly be used across this project's *entire* reachable n range without ever needing the MC fallback — implement the MC fallback anyway (for robustness / future-proofing / matching the sibling's pattern), but set its crossover threshold generously (e.g. n=12, `K=4096`) since it will likely never trigger in practice.

## Code Examples

### Parameter-shift gradient of a weight-1 parameter
```python
# Source: derived in this research (Pattern 1), verified against
# expected_single_qubit_probs' closed form (this repo's iqp_photonic_encoding.py)
import numpy as np

def shifted_distribution(n, thetas, k, sign):
    shifted = list(thetas)
    shifted[k] += sign * (np.pi / 4)
    dist, residual = photonic_iqp_distribution(n, shifted)  # from iqp_photonic_encoding.py
    return dist, residual

def dq_dtheta_k(n, thetas, k, bin_index_fn, K):
    dist_plus, _ = shifted_distribution(n, thetas, k, +1)
    dist_minus, _ = shifted_distribution(n, thetas, k, -1)
    q_plus = np.zeros(K)
    q_minus = np.zeros(K)
    for bitstring, p in dist_plus.items():
        q_plus[bin_index_fn(bitstring)] += p
    for bitstring, p in dist_minus.items():
        q_minus[bin_index_fn(bitstring)] += p
    return q_plus - q_minus  # exact, no division (Pattern 1)
```

# Source: derived in this research (Pattern 2); kernel-matrix formula ported

def mmd2_grad_theta_k(q_theta, p_real, kernel_matrix, dq_dtheta_k):

### Poly-vs-exponential model comparison with AIC (extending the sibling project's pattern)
```python
# Pattern source: iqp_bp/experiments/scaling_summary.py::_fit_scaling_groups
# (log-linear OLS + R²) -- extended here with scipy.optimize.curve_fit + AIC
# to satisfy TRAIN-02's explicit "e.g. R2/AIC" ask.
import numpy as np
from scipy.optimize import curve_fit

def exp_model(n, a, b, c):
    return a * np.exp(-b * n) + c

def poly_model(n, a, b, c):
    return a * np.power(n, -b) + c   # or a*n**b + c depending on expected sign

def aic(residuals, k_params):
    n_obs = len(residuals)
    rss = np.sum(residuals ** 2)
    return n_obs * np.log(rss / n_obs) + 2 * k_params

def fit_and_compare(ns, variances):
    ns = np.asarray(ns, dtype=float)
    ys = np.asarray(variances, dtype=float)
    exp_params, _ = curve_fit(exp_model, ns, ys, p0=[ys[0], 0.5, 0.0], maxfev=10000)
    poly_params, _ = curve_fit(poly_model, ns, ys, p0=[ys[0], 1.0, 0.0], maxfev=10000)
    exp_resid = ys - exp_model(ns, *exp_params)
    poly_resid = ys - poly_model(ns, *poly_params)
    return {
        "exp": {"params": exp_params, "aic": aic(exp_resid, 3), "r2": 1 - np.sum(exp_resid**2)/np.sum((ys-ys.mean())**2)},
        "poly": {"params": poly_params, "aic": aic(poly_resid, 3), "r2": 1 - np.sum(poly_resid**2)/np.sum((ys-ys.mean())**2)},
    }
```

## Open Questions

1. **Bitstring-to-bin-index mapping for the K=2^n MMD² target, at each sweep n.**
   - What we know: v1.0's `compute_p_real`/`make_natural_bin_centers` machinery generalizes mechanically to any `rows·cols=K` grid, and `radius_sort_order`/`fock_state_sort_order` already establish this project's precedent of choosing a "smoothness-preserving" index correspondence rather than an arbitrary one.
   - What's unclear: whether the *specific* ordering (raw binary integer value of the bitstring vs. a Gray-code-style adjacency-preserving order vs. reusing `radius_sort_order`'s literal sort) is locked by anything already shipped — it isn't; this repo has no existing bitstring→2D-grid convention.
   - Recommendation: pick the simplest option (bitstring's integer value as a raw row-major index into a `2^⌈n/2⌉ × 2^⌊n/2⌋` grid) and state it explicitly in the write-up per this repo's standing practice — the gradient-variance *magnitude* is not obviously sensitive to this choice (unlike an actual generative-training run, where spatial smoothness would matter), so low-risk to leave as a documented, non-locked implementation choice for planning.

2. **Whether to cap tracked parameter indices, and at what number.**
   - What we know: the sibling project caps at `min(5, actual_m)`; this repo's weight-1 circuits have `m=n` parameters, so tracking all of them multiplies total compute by `n` for no clear benefit (variance across draws, not across parameter identity, is the quantity of interest for TRAIN-01).
   - What's unclear: CONTEXT.md's "Claude's discretion" section explicitly leaves "implementation details ... batching" open but doesn't name this specific choice.
   - Recommendation: cap at 3-5 tracked parameters per setting (this is the single biggest lever on total sweep runtime after n itself — the difference between capping at 5 and tracking all n params at n=8 is a factor of ~1.6×, but at larger n where m grows, it compounds).

3. **Whether the n=8 (weight-1) / n=6 (mixed) stretch points are worth the multi-day compute cost given the ~2026-08-20 mid-milestone checkpoint.**
   - What we know: the measured/extrapolated costs above (2.9 days for n=8 weight-1 at 1000 evals/init-scheme × 2 init schemes ≈ 5.8 days total).
   - What's unclear: how much other Phase 17 work (curve fitting, write-up, cross-referencing) needs to happen in the same window.
   - Recommendation: treat n=7 as the safe ceiling for the core sweep, and explicitly time-box (in the plan, not as a phase-level decision — the phase-level "no time-box" is the owner's call, not mine to override) an attempt at n=8/n=6-mixed as a background/overnight job that can be abandoned without blocking the rest of the phase if it doesn't finish — this operationalizes "push until compute genuinely can't go further" without letting it silently consume the whole remaining milestone.
